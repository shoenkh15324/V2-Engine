# 스케일링 벤치마크

## 목적

> **연구 질문:** "워커나 액터를 추가하면 성능이 선형적으로 향상되는가?"

**워커 및 액터 스케일링 효율성**을 측정합니다. 이상적인 병렬 시스템에서는 2x 워커 = 2x 쓰루풋이지만, 현실은 다릅니다.

## 설계 원칙

### 왜 중요한가

스케일링은 하드웨어 투자가 보상받을 수 있는지를 결정합니다. 코어를 추가해도 도움이 되지 않으면 시스템은 동기화 바인드입니다.

### 측정 방법

**테스트 1: 워커 스케일링** (액터 고정)
```
각 worker_count in [1, 2, 4, 8, 16]에 대해:
    throughput = measure(worker_count, 고정된 actors, iterations)
```

**테스트 2: 액터 스케일링** (워커 고정)
```
각 actor_count in [1, 2, 4, 8, 16]에 대해:
    throughput = measure(고정된 workers, actor_count, iterations)
```

### 파라미터 참조

| 파라미터 | 기본값 | 설명 |
|---------|--------|------|
| `--workers` | 변동 | 워커 스레드 수 |
| `--actors` | 변동 | 대상 액터 수 |
| `--iterations` | 200,000 | 전체 메시지 수 |
| `--maxbatch` | 32 | 워커당 최대 배치 크기 |
| `--warmup` | 0 | 웜업 메시지 수 |

## 실험 결과 (2026-08-31 실측)

### 실험 1: 워커 스케일링 (단일 프로듀서)

**조건:** actors=1, producers=1, iterations=200,000

| Workers | 쓰루풋 (msgs/sec) | 효율성 | 비고 |
|---------|-------------------|--------|------|
| 1 | **19,660,538** | 1.00x | 기준 |
| 4 | 28,627,961 | 1.46x | **최적** |
| 8 | 28,956,333 | 1.47x | |
| 16 | 22,047,975 | 1.12x | |

**분석:**
- **workers=4~8에서 최적**: 28~29M msgs/sec
- **workers=16에서 감소**: 22M msgs/sec (물리 코어 8개 초과)
- **핵심:** 8 물리 코어까지는 스케일링 양호, SMT(16 Logical) 초과 시 성능 하락

### 실험 2: 액터 스케일링 (단일 프로듀서)

**조건:** workers=4, producers=1, iterations=200,000

| Actors | 쓰루풋 (msgs/sec) | 비고 |
|--------|-------------------|------|
| 1 | 28,627,961 | 기준 |
| 2 | 19,854,019 | |
| 4 | 17,865,288 | |
| 8 | 13,681,192 | |
| 16 | 14,821,882 | |

**분석:**
- **actors=1에서 최적**: 28.6M msgs/sec
- **actors 증가에 따라 감소**: dispatch() 경로 싱글 스레드 병목
- **핵심:** 단일 프로듀서에서는 액터 수 증가가 오히려 독 (dispatch 병목)

### 실험 3: 멀티 프로듀서 스케일링

**조건:** workers=4, actors=16, iterations=200,000

| Producers | 쓰루풋 (msgs/sec) | 비고 |
|-----------|-------------------|------|
| 1 | 14,821,882 | 단일 프로듀서 |
| 2 | 15,690,698 | |
| 4 | 16,780,369 | |
| 8 | 16,707,232 | |
| 16 | 14,478,845 | |

**분석:**
- **producers=4~8에서 최적**: 16.7M msgs/sec
- **producers=16에서 감소**: CAS 경쟁 포화
- **핵심:** 멀티 프로듀서는 dispatch 병목을 완화하지만, CAS 경쟁이 한계

### 실험 4: 멀티 프로듀서 × 멀티 워커 (최적 조합)

| Workers | Actors | Producers | 쓰루풋 (msgs/sec) | 비고 |
|---------|--------|-----------|-------------------|------|
| 1 | 16 | 8 | 48,695,332 | |
| 4 | 16 | 4 | 59,378,296 | |
| **4** | **16** | **8** | **73,272,523** | **최적** |
| 8 | 16 | 8 | 66,451,695 | |

**분석:**
- **4W 16A 8P에서 최적**: 73.3M msgs/sec
- **핵심:** 4 워커 + 16 액터 + 8 프로듀서 = 최적 병렬화

### 스케일링 붕괴 분석

**조건:** 단일 프로듀서 (producers=1)

| Workers | Actors | 쓰루풋 (msgs/sec) | 붕괴 여부 |
|---------|--------|-------------------|----------|
| 1 | 1 | 19,660,538 | |
| 4 | 4 | 17,865,288 | |
| 8 | 8 | 13,681,192 | |
| **16** | **16** | **299,698** | **붕괴 (100배↓)** |

**붕괴 원인:**
1. `receiveMsg()` → `enqueue()` → `dispatch()` 경로가 싱글 스레드에서 실행
2. 16 워커가 readyQueue 뮤텍스를 경쟁 → 세마포어 thundering herd
3. MPMC 큐 컨슈머 CAS 경쟁: W=8에서 50% 감소, W=16에서 80% 감소

**붕괴 우회 방법:**
- 멀티 프로듀서 사용 (4W 16A 8P: 73.3M msgs/sec)

## 기술적 상세

### 스케일링 패턴 시각화

```
쓰루풋 (단일 프로듀서, 워커 스케일링)
  ↑
  │                 ★ 29.0M (W=8)
  │           ★ 28.6M (W=4)
  │
  │                          ★ 22.0M (W=16)
  │ ★ 19.7M (W=1)
  └──────────────────────────────────→ Workers
      1     4     8     16

쓰루풋 (단일 프로듀서, 액터 스케일링)
  ↑
  │ ★ 28.6M (A=1)
  │
  │     ★ 19.9M (A=2)
  │
  │           ★ 17.9M (A=4)
  │
  │                    ★ 13.7M (A=8)
  │                          ★ 14.8M (A=16)
  └──────────────────────────────────→ Actors
      1     2     4     8     16

쓰루풋 (4W, 멀티 프로듀서 스케일링)
  ↑
  │                    ★ 16.7M (P=4~8)
  │
  │     ★ 15.7M (P=2)
  │
  │ ★ 14.8M (P=1)
  │
  │                          ★ 14.5M (P=16)
  └──────────────────────────────────→ Producers
      1     2     4     8     16
```

### 동기화 비용 분석

```
단일 워커 (W=1):
  세마포어: ~0ns (단일 워커, 세마포어 비용 최소)
  뮤텍스:   ~20-50ns (Mailbox push/pop)
  Handle:   ~5ns (원자적 카운터)
  총:       ~25-55ns/메시지

멀티 워커 (W=4):
  세마포어: ~200ns (웨이크업 + 컨텍스트 스위칭)
  뮤텍스:   ~50ns (경쟁 증가)
  Handle:   ~5ns
  총:       ~255-300ns/메시지

멀티 워커 (W=16):
  세마포어: ~1,000ns (thundering herd)
  뮤텍스:   ~200ns (치열한 경쟁)
  Handle:   ~5ns
  총:       ~1,200ns/메시지
```

## 분석

### 핵심 발견

1. **최적 워커 수: 4~8개** (단일 프로듀서)
   - 8 물리 코어까지는 스케일링 양호
   - 16 Logical 초과 시 SMT 경쟁으로 성능 하락

2. **최적 액터 수: 1개** (단일 프로듀서)
   - 멀티 액터는 dispatch 병목을 악화
   - 멀티 프로듀서 사용 시에만 멀티 액터 유리

3. **스케일링 붕괴: 16W 16A + 단일 프로듀서**
   - 100배 성능 하락 (29.0M → 299K)
   - **원인**: dispatch 경로 싱글 스레드 + readyQueue 뮤텍스 경쟁

4. **최적 조합: 4W 16A 8P**
   - 73.3M msgs/sec 달성
   - 멀티 프로듀서가 dispatch 병목 완화

### 상용 엔진 비교

| 엔진 | 스케일링 패턴 | V2 대비 |
|------|-------------|---------|
| **V2-Engine** | 4W에서 최적, 16W에서 붕괴 (단일 P) | 기준 |
| **CAF** | 멀티 워커 스케일링 안정적 | V2가 단일 워커에서 3배 빠름 |
| **SObjectizer** | 협력 FIFO로 안정적 | V2가 direct ch에서 1.7배 빠름 |
| **Theron** | 뮤텍스 기반, 4코어 이후 붕괴 | 유사한 붕괴 패턴 |
| **Actix** | N:N 스케일링 안정적 | V2가 절대 성능에서 우위 |

### 권장사항

| 우선순위 | 권장사항 | 예상 효과 |
|---------|---------|----------|
| 최우선 | 멀티 프로듀서 사용 (4P~8P) | 붕괴 우회, 73M+ msgs/sec |
| 높음 | workers=4~8 (단일 프로듀서) | 28~29M msgs/sec |
| 중간 | 16 Logical 초과 시 주의 | SMT 경쟁으로 성능 하락 |
| 낮음 | 핸들러 무게에 맞춰 워커 수 결정 | 병렬 활용 최적화 |

## 결론

### 요약

단일 프로듀서에서는 4~8 워커에서 최적(28~29M msgs/sec)이지만, 16 워커 + 16 액터에서 100배 성능 붕괴가 발생합니다. 멀티 프로듀서(4P~8P)를 사용하면 붕괴를 우회하여 73.3M msgs/sec를 달성할 수 있습니다. V2-Engine은 단일 워커에서 CAF 대비 3배 빠르지만, 멀티 워커 스케일링은 CAF/Actix 대비 열세입니다.

| 단일 워커 최적 | workers=1, actors=1 |
| 멀티 워커 확장 | 반드시 멀티 프로듀서 사용 |
