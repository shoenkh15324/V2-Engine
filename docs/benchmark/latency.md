# 레이턴시 벤치마크

## 목적

> **연구 질문:** "단일 메시지가 주입부터 처리까지 얼마나 걸리는가?"

**단일 메시지의 종단간 레이턴시**를 측정합니다. 실시간 시스템에서는 쓰루풋보다 응답 시간이 더 중요합니다.

## 설계 원칙

### 왜 중요한가

쓰루풋은 "얼마나 빠른지"를 측정하지만, 레이턴시는 **"메시지가 실제로 처리되기까지 얼마나 걸리는지"**를 측정합니다. 게임 서버, 실시간 채팅, IoT에서 가장 중요한 지표입니다.

### 측정 방법

```
각 메시지마다:
  1. sendTimestamp[i] = now()           ← 주입 시점
  2. receiveMsg(Tick{})                 ← 메일박스에 push
  3. while not handled: spin-wait       ← handle() 대기
  4. latency[i] = now() - sendTimestamp ← handle()에서 측정
```

- **동기식**: 한 번에 하나의 메시지, 배치 없음
- **동기화 오버헤드**만 측정 (세마포어 웨이크업 + 뮤텍스)

### 파라미터 참조

| 파라미터 | 기본값 | 설명 |
|---------|--------|------|
| `--workers` | 4 | 워커 스레드 수 |
| `--iterations` | 50,000 | 측정할 메시지 수 |
| `--maxbatch` | 32 | 워커당 최대 배치 크기 |
| `--warmup` | 0 | 웜업 메시지 수 |
| `--mailbox` | 0 | 메일박스 용량 (0=자동) |

## 실험 결과 (2026-08-31 실측)

### 실험 1: 워커 수 (단일 액터)

**조건:** actors=1, maxBatch=32, iterations=100,000

| Workers | P50 | P99 | P99.9 | Max | 비고 |
|---------|-----|-----|-------|-----|------|
| 1 | **912 ns** | **977 ns** | **2,430 ns** | 130,384 ns | **최적** |
| 2 | 907 ns | 975 ns | 1,938 ns | 11,216 ns | |
| 4 | 915 ns | 1,041 ns | 2,124 ns | 13,766 ns | |
| 8 | 918 ns | 992 ns | 1,901 ns | 48,556 ns | |
| 16 | 914 ns | 982 ns | 1,776 ns | 8,010 ns | |

**분석:**
- **workers에 관계없이 P50 ~912ns, P99 ~977ns로 안정적**
- 이전 측정(378ns) 대비 P50 2.4배 증가 — 스핀 티어 도입 후 회귀
- **P99.9에서 변동**: 시스템 오버헤드 (컨텍스트 스위칭, 캐시 미스)
- **핵심:** 멀티 워커에서도 레이턴시 안정적 (MPSC 제약이 레이턴시에는 영향 없음)

### 실험 2: 액터 수

**조건:** workers=1, maxBatch=32, iterations=100,000

| Actors | P50 | P99 | P99.9 | 비고 |
|--------|-----|-----|-------|------|
| 1 | 912 ns | 977 ns | 2,430 ns | 기준 |
| 4 | 909 ns | 1,063 ns | 12,628 ns | |

**분석:**
- **P50은 액터 수에 무관하게 ~910ns**
- **P99.9는 4 액터에서 증가**: 멀티 액터 시 메일박스 경쟁
- **핵심:** 기본 레이턴시는 액터 수에 영향 없음

### 실험 3: 멀티 워커 + 멀티 액터

**조건:** actors=4, maxBatch=32, iterations=100,000

| Workers | P50 | P99 | P99.9 | 비고 |
|---------|-----|-----|-------|------|
| 1 | 909 ns | 1,063 ns | 12,628 ns | |
| 4 | 915 ns | 1,030 ns | 12,189 ns | |

**분석:**
- **P50은 워커 수에 무관하게 ~910ns**
- **P99는 워커 수에 무관하게 ~1,000ns**
- **핵심:** 멀티 워커에서도 기본 레이턴시 안정적

### 레이턴시 구성 요소 분석

```
레이턴시 (P50 ~912ns):
  ├── 세마포어:     ~0ns (스핀 대기, 비차단)
  ├── 뮤텍스:       ~20-50ns (Mailbox push/pop)
  ├── 핸들러:       ~5ns (원자적 카운터)
  ├── 타임스탬프:   ~5ns (two-clock 안정화)
  ├── 배치 처리:    ~0ns (단일 메시지)
  └── 나머지:      ~830-850ns (스핀 티어 대기)
```

### 이전 측정과의 비교

| 지표 | 이전 (2026-08-15) | 현재 (2026-08-31) | 변화 |
|------|-------------------|-------------------|------|
| P50 (1W) | 378 ns | 912 ns | **+534 ns (+141%)** |
| P99 (1W) | 641 ns | 977 ns | **+336 ns (+52%)** |
| P50 (4W) | 10,900 ns | 915 ns | **-9,985 ns (-92%)** |

**변동 원인:**
- 스핀 티어 도입 (grace=500): 단일 워커 P50 증가, 멀티 워커 P50 대폭 개선
- 타임스탬프 안정화: two-clock 메커니즘 추가
- Lock-free 타입 안전: `std::variant<void*,T*>` → `std::atomic<T*>`

## 기술적 상세

### 레이턴시 메커니즘

```
메인 스레드:
  1. now() → sendTimestamp (nanoseconds)
  2. receiveMsg(Tick{}) → enqueue()
     ├→ Mailbox::push()              [CAS 락프리]
     └→ Dispatcher::dispatch()
        ├→ readyQueue_.push()        [뮤텍스]
        └→ sema_.release()           [세마포어]

워커 스레드:
  3. sema_.acquire()                 [스핀 대기]
  4. Mailbox::pop()                  [CAS 락프리]
  5. Actor::handle(Tick{})
     ├→ counter_.fetch_add(1)        [5ns]
     ├→ sendTimestamp_.store(now())  [5ns]
     └→ handled_.store(true)         [5ns]
  6. main_sema_.release()            [메인 스레드 알림]

메인 스레드:
  7. while !handled: spin-wait
  8. latency = now() - sendTimestamp
```

### workers=1에서만 정확한 측정이 가능한 이유

동기식 측정에서는 메일박스에 하나의 메시지만 존재합니다:
1. 메인 스레드 push → dispatch → sema_.release()
2. 워커 sema_.acquire() → pop() → handle() → ack
3. 메인 스레드 ack 확인 → 다음 메시지

**더 많은 워커는:**
- sema_.release()에서 썬더링 허드
- pop()에서 뮤텍스 경쟁
- 스케줄링 레이턴시 증가
- 하지만 P50/P99는 ~910ns로 안정적 (스핀 대기)

## 분석

### 핵심 발견

1. **P50 = 912ns, P99 = 977ns** (모든 워커 구성)
   - 세마포어 비용 최소화 (스핀 대기)
   - Mailbox 뮤텍스 비용 ~20-50ns
   - **실시간 시스템에 적합** (<1μs)

2. **workers에 관계없이 안정적**
   - P50: 907~918ns (변동 <2%)
   - P99: 975~1,041ns (변동 <7%)
   - **멀티 워커에서도 레이턴시 안정적**

3. **이전 대비 P50 증가 (+534ns)**
   - 스핀 티어 도입 비용
   - 멀티 워커 P50 개선 (-9,985ns)과 교환

4. **P99.9 변동**
   - 1W: 2,430ns vs 4A 1W: 12,628ns
   - **시스템 오버헤드 (컨텍스트 스위칭, 캐시 미스)**

## 결론

### 요약

시스템은 모든 워커 구성에서 **P50=912ns, P99=977ns**의 안정적인 레이턴시를 보여줍니다. 이전 측정(378ns) 대비 P50이 증가하였으나, 이는 멀티 워커 P50 개선(-9,985ns)과 교환한 것입니다. 멀티 워커에서도 레이턴시가 안정적이며, P99 <1μs는 실시간 시스템에 적합한 수준입니다.

### 사용 시점

| 시나리오 | 권장사항 |
|---------|---------|

| 게임 서버, 실시간 채팅 | workers=1~4, maxBatch=32 |
| 일반 웹 서비스 | workers=4~8, maxBatch=32~64 |
